# PrepCanvas implementation and product review — 2026-09-29

Reviewed commit: `41021b8` (current `origin/main` when fetched). Local main was ten commits behind before the review branch was synchronized. Tracking task: TASK-041.

## Assessment

PrepCanvas now implements a useful personal study loop for user subjects, beyond the original synthetic demo. The strongest decision is separating assistant-built content from deterministic study sessions: a learner can keep practising without a provider, API key, or network dependency. The next investment should be reliable data handling and trustworthy learning feedback before adding more automation.

The current implementation is promising for controlled personal use, but the import and grading findings below should block the next release. A green test suite does not yet demonstrate safe recovery from malformed content or isolation of all session state.

## What is working well

- The product flow is coherent: library → Content → diagnostic/learning → practice → exam → progress. User subjects now have real content instead of metadata-only placeholders.
- A single package schema, source/generated question labels, and model-answer rubric self-check provide useful guardrails. They catch impossible rubrics and broken cross-references early.
- Domain modules for storage, grading, readiness, packages, practice, exams, and transfer are small enough to inspect independently. SQLite operations close connections and use transactions within individual operations.
- Practice prioritizes unanswered questions, mock exams delay feedback, and the clock records overtime honestly rather than claiming strict exam enforcement.
- Readiness deduplicates question evidence, decays it over time, and is documented as a heuristic. The UI shows evidence volume alongside topic scores.
- Privacy boundaries are explicit: application storage is local; the learner's chosen assistant is a separate recipient. Synthetic public content and ignored private directories are good defaults.
- The current automated suite has 163 passing tests, including AppTest flows and package/transfer checks. The task board is mechanically checked against task files.

## Product and design gaps

**Source labels are not verifiable grounding.** Today a nonempty label and a model answer that matches its own rubric can validate even if the educational claim is wrong. TASK-014 should expose source excerpts and locators, including missing-reference states. Keep human review in the build workflow.

**Readiness is useful direction, not yet an independent assessment.** Coaching, practice, and exams draw from the same pool. Repeating remembered answers can produce strong scores without demonstrating transfer. TASK-018 should compare readiness before a sitting with subsequent performance and distinguish first-seen/repeated questions and timed/overtime attempts. Rebuilt packages also need an explicit policy for old evidence and reused question ids.

**Build onboarding still requires technical coordination.** Learners switch to an assistant and import JSON. That is a reasonable MVP tradeoff, but the app should first handle bad outputs safely. Observe a few complete synthetic onboarding sessions before deciding whether TASK-030 is the right solution. Local extraction (TASK-013) and clear errors may remove much of the friction.

**The UI module is growing.** At roughly 1,100 lines it mixes styling, setup, navigation, persistence, and exam state. Extract screen rendering and session controllers incrementally when fixing affected flows; avoid a standalone rewrite before behavior is covered.

**Presentation and release labels lag implementation.** Repository tags stop at v0.1.1, the package version is 0.1.1, and recent changes are under Unreleased. Previous board headings v0.2.0–v0.2.3 were not evidence of releases. The board now distinguishes delivered work from tagged releases. TASK-031 includes current-flow visual and keyboard QA as well as new media.

## Recommended sequence

1. TASK-042–TASK-046: contain archives, preserve previous data on failure, make validation recoverable, correct language handling, and isolate exam state. Add regression coverage to each fix.
2. TASK-014 and TASK-018: let learners inspect evidence and make the interpretation of readiness defensible.
3. TASK-013 and TASK-031: improve material reading and validate the current onboarding/study flow on desktop and phone. Complete release QA before tagging the next version.
4. Only then reconsider CLI launching, spaced review, and offline model integration. No new provider integration is needed to close the current reliability gaps.

## Verification and limits

- Full suite at reviewed commit: `./scripts/run_tests.sh -q` → **163 passed**.
- Synthetic temporary-directory probes reproduced traversal, destructive replacement, malformed-container validation crashes, and Cyrillic misgrading.
- Streamlit AppTest with two synthetic packages reproduced cross-subject timer reuse without any app exceptions.
- All experiments used temporary databases and private directories. No learner documents, existing progress, or private packages were inspected or modified.
- This was a code, documentation, and AppTest review. It did not include browser visual/accessibility QA, a real learner usability study, or calibration against real exam outcomes.
